## Keep async code non-blocking

FastAPI runs `async def` handlers on the event loop and plain `def` handlers in a thread pool. Blocking inside `async def` stalls every request on that worker.

1. Declare a path operation with plain `def` when it calls a library that does not support `await`, such as many database drivers and SDKs. FastAPI's documentation recommends exactly this.
2. Inside `async def`, use only asynchronous clients (for example `httpx.AsyncClient` and an async database driver), and never call `time.sleep`, synchronous HTTP clients or blocking file operations.
3. Move CPU-heavy work to a worker process or task queue. Background tasks that run in the web process are lost on restart, so use a durable queue for work that must complete.

## Set timeouts on HTTP clients

| Client | Default | Do |
|---|---|---|
| Requests | No timeout at all | Always pass `timeout=(connect, read)` |
| HTTPX | Times out after 5 seconds of network inactivity | Set a timeout that fits each dependency on the client |

Reuse one client per dependency for connection pooling. See [retry rules](reliability-performance.md).

## Validate at the edge and control responses

1. Declare request bodies, query parameters and headers as typed Pydantic models, so invalid input is rejected before your code runs.
2. Declare a `response_model` (or a return type) for every endpoint, so internal fields such as password hashes or internal flags cannot leak into responses.
3. Register exception handlers that return RFC 9457 problem details (see [api-design.md](api-design.md)), and run with debug mode off outside development so stack traces never reach clients.
4. Put authentication and authorisation in reusable dependencies (`Depends`) applied at router level, so a new endpoint cannot forget them.

## Add sign-in with OpenID Connect

FastAPI's "Simple OAuth2 with Password and Bearer" tutorial explicitly uses insecure tokens to teach the password grant. Do not copy it for external-provider sign-in: RFC 9700 forbids the resource owner password credentials grant.

1. Use the authorisation code flow with PKCE through a maintained library, for example Authlib's Starlette integration, which FastAPI applications can use.
2. Register the provider with its discovery document (`server_metadata_url`) and request the `openid` scope, so endpoints and signing keys come from the provider rather than hard-coded values.
3. Start sign-in with `authorize_redirect` and finish it with `authorize_access_token`, which parses the ID token. Confirm, in the library version you use, that `state` and `nonce` are generated and checked and that PKCE is enabled; if any is not automatic, configure it.
4. Validate the ID token's issuer, audience, expiry and signature (see [security.md](security.md)), then map the provider's subject identifier to your user record. Never key accounts on email address alone.
5. Issue your own session after sign-in, regenerate it at login, and clear it at logout.
6. Register exact redirect URIs with the provider for each environment, and keep the client secret in the secret store.

## Configure sessions safely

Starlette `SessionMiddleware` uses signed cookies: users cannot modify their contents but can read them.

1. Never store tokens, secrets or personal data in the session cookie. Store a session identifier and keep the data server-side, or encrypt it.
2. Set `https_only=True` (the default is `False`) and keep `same_site` at `lax` or set it to `strict`.
3. Set `max_age` to your absolute session timeout; the default is two weeks.
4. Load `secret_key` from the secret store, make it long and random, and plan how to rotate it.
5. Protect state-changing endpoints that rely on the cookie against CSRF (see [security.md](security.md)).

## Review Alembic migrations

Alembic requires manual review and correction of every autogenerated migration.

1. Expect renamed tables and columns to appear as a drop plus an add, and rewrite them by hand (or, better, follow the expand and contract sequence in [data-and-privacy.md](data-and-privacy.md)).
2. Run statements that cannot run inside a transaction, such as PostgreSQL's `CREATE INDEX CONCURRENTLY`, inside `op.get_context().autocommit_block()`, and enable `transaction_per_migration` in `env.py`, because the block commits everything that ran before it.
3. Test each migration's upgrade and downgrade against a real database of the production engine, not SQLite.

## Test FastAPI services

1. Use pytest with fixtures, and exercise endpoints through the framework's test client or an `httpx` client bound to the app.
2. Replace dependencies in tests with `app.dependency_overrides`, and clear the overrides after each test.
3. Run integration tests against the same database engine as production, in a container.
4. Use Hypothesis for parsers, validators and pricing rules, and mutmut on critical modules (see [testing.md](testing.md)).

## Other Python traps

- Never unpickle untrusted data, and load untrusted YAML with `yaml.safe_load`; OWASP's deserialisation guidance explains why.
- Avoid mutable default arguments (`def f(items=[])`); the default is shared between calls.
- Use timezone-aware `datetime` objects in UTC, and parse money with `decimal.Decimal`, never `float`.
- Commit a lockfile and install with hashes (for example pip's `--require-hashes` mode or a lock-based tool), and run a vulnerability audit such as `pip-audit` in CI (see [supply-chain.md](supply-chain.md)).
- Run a type checker and a linter in CI, and do not add `# type: ignore` or `noqa` comments without a reason.
